# Datasets & Data Pipelines

Training Lifecycle walked through the stages of training. But every one of those stages is only as good as the data it's trained on. This page covers that data itself — where it comes from, what "cleaning" it actually means, and why data quality matters more than almost any other decision in building a model.

## What's actually in a pretraining corpus

Pretraining (Training Lifecycle) needs an enormous amount of text — trillions of tokens. In practice, that means scraping the open web (using something like Common Crawl), plus adding licensed and curated sources: books, code repositories, academic papers, Wikipedia.

But scale by itself isn't the goal. A collection of text this large is inevitably messy — full of noise, repetition, and content of wildly uneven quality. That's exactly the problem the cleaning pipeline exists to fix, before any of this text reaches training.

## Cleaning and deduplication

Raw scraped text is full of boilerplate, broken formatting, spam, and near-duplicate pages.

**Deduplication** — removing exact and near-exact copies of the same document — matters more than it might sound. If the same content shows up many times, the model can end up memorizing and over-weighting whatever's repeated the most, at the expense of everything it only saw once.

Filtering also removes low-quality or harmful content. Increasingly, it also **decontaminates** the data — removing anything that overlaps with the questions used to test the model later (Evaluation & Monitoring). Without that step, a good test score might just mean the model memorized the test's answers, not that it's genuinely capable. This is the same problem as a model that's "overfit" — it looks great on the exact data it was tested on, but that success doesn't generalize.

## Synthetic data

More and more, part of a training set — especially for the smaller, later stages like SFT (Training Lifecycle) — is generated by another model instead of collected from humans. A strong existing model produces example responses; those responses are sometimes filtered or ranked by a second model or by humans; and the result becomes training data for the next model.

This is now standard practice. But it carries a real risk if it's done carelessly across several generations: training too heavily on a previous model's own output can amplify that model's quirks and mistakes, instead of fixing them. Researchers call this effect **model collapse**.

## Data contamination

**Contamination** happens when evaluation data — the actual questions a model will later be tested on — accidentally ends up in its training data. This can happen through careless scraping (a benchmark's questions and answers are sitting somewhere on the public web) or through synthetic data generation.

A contaminated model can score deceptively well on a test, simply because it memorized the answers, not because it actually has the capability the test was supposed to measure. This is exactly why decontamination gets its own dedicated pipeline stage — it isn't something you can just hope deduplication happens to catch.

## Why this matters for system design

Every stage of training — pretraining, fine-tuning, preference tuning — is only as good as the data behind it. A bigger model trained on worse data will routinely lose to a smaller model trained on better data.

This is the same "garbage in, garbage out" principle as any data pipeline elsewhere in this course, just with much higher stakes. A bug in a normal ETL pipeline (Batch vs. Stream Processing) corrupts a report — annoying, but fixable. A bug in a training data pipeline gets baked directly into the model's weights, and it's far more expensive to notice and fix after the fact.

## Real-world examples

- **Common Crawl** — the enormous, ongoing crawl of the open web that most large pretraining datasets are built from, in some cleaned-up form.
- **The Pile, RedPajama, FineWeb** — publicly documented, cleaned datasets, released specifically so the cleaning process itself is visible and reproducible.
- **GitHub Copilot / code models** — trained heavily on public code repositories, which is what first put questions about licensing and attribution for training data in the news.
- **"Model collapse"** — an active area of research, since more and more of the web is now written by LLMs, and future models will inevitably scrape some of that.
